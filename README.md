# HR Notify Agent — Open Command Demo

نسخة الديمو النهائية: مساعد HR بيستقبل أوامر مفتوحة (مكتوبة أو بالصوت)، يحدد المستهدفين والقناة المناسبة (إيميل/مكالمة/الاتنين)، ويعرض خطة للموافقة قبل أي تنفيذ. وبعد التنفيذ، **بيتابع الردود فعليًا**: يرد لوحده على الأسئلة الروتينية، ويصعّد أي حاجة مش واضحة لـ HR Manager. 3 شاشات: **Chat** (أوامر متواصلة، مش بتنسى السياق)، **Monitor** (متابعة كل الحملات، مش تاسك واحدة)، **Settings** (دليل الموظفين + سياسات الشركة). بالكامل ثنائي اللغة (إنجليزي افتراضي / عربي).

## النشر (Deployment) — خطوة بخطوة

### المنصة المقترحة: Railway
السبب: HTTPS تلقائي (بيحل مشكلة المايك نهائيًا من غير ngrok)، وبيدعم process دائم الشغل (ضروري للـ Scheduler)، وسهل جدًا (git push وخلاص).

### الخطوة 1: ارفع الكود على GitHub
```bash
cd hr-notify-agent
git init
git add .
git commit -m "initial commit"
# اعمل repo جديد على GitHub، وبعدين:
git remote add origin https://github.com/YOUR-USERNAME/hr-notify-agent.git
git push -u origin main
```

### الخطوة 2: اعمل مشروع على Railway
1. روح [railway.app](https://railway.app) واعمل حساب (بحساب GitHub أسهل)
2. **New Project → Deploy from GitHub repo** → اختار الـ repo بتاعك
3. Railway هيكتشف `Procfile` و`requirements.txt` تلقائيًا ويبدأ البناء

### الخطوة 3: أضف Persistent Volume (مهم جدًا - من غيره بياناتك بتتمسح)
1. من صفحة المشروع في Railway → **Settings → Volumes → New Volume**
2. اسمه أي اسم، واربطه بمسار `/data`
3. من **Variables** أضف:
```
DATA_DIR=/data
```

### الخطوة 4: أضف باقي متغيرات البيئة
من **Variables** في Railway، انسخ كل محتوى `.env.example` وحط القيم الحقيقية بتاعتك (`ANTHROPIC_API_KEY`, `VAPI_API_KEY`, `SMTP_USER`, إلخ). **متنساش** تضيف:
```
MOCK_CLAUDE=false
MOCK_CALLS=false
MOCK_INBOX=false
MOCK_EMAIL=false
```
(عشان النظام يشتغل بجد مش بوضع تجريبي)

### الخطوة 5: اتأكد إنه شغال على الدومين المؤقت
Railway هيديك رابط تلقائي زي `https://hr-notify-agent-production.up.railway.app` — افتحه وجرب كل حاجة (المايك هيشتغل فورًا لأنه HTTPS حقيقي).

### الخطوة 6: اربط الدومين بتاعك
1. من Railway: **Settings → Networking → Custom Domain**
2. اكتب الدومين بتاعك (مثلاً `hr.yourcompany.com`)
3. Railway هيديك سجل **CNAME** لازم تضيفه عند مزود الدومين بتاعك (Namecheap, GoDaddy, Cloudflare...):
   - اسم السجل: `hr` (أو الـ subdomain اللي اخترته)
   - القيمة: اللي Railway إداهولك (زي `xxxx.up.railway.app`)
4. استنى من 5 دقايق لساعة (حسب مزود الدومين) لحد ما الـ DNS ينتشر
5. Railway هيصدر شهادة SSL تلقائيًا (Let's Encrypt) — من غير أي خطوة إضافية منك

### الخطوة 7: ضيّق CORS على الدومين بتاعك (أمان)
من **Variables** في Railway، أضف (من غير أي تعديل كود أو deploy تاني):
```
ALLOWED_ORIGINS=https://hr.yourcompany.com
```

### إزاي تتأكد إنه فاضل شغال (Always-On)
Railway على الخطة المدفوعة ($5/شهر فأكتر) بيخلي الـ process شغال باستمرار من غير ما ينام — مهم جدًا عشان الـ Scheduler يفضل بيفحص الردود دوريًا حتى لو محدش فاتح الموقع. الخطة المجانية بتنام بعد فترة من غير استخدام، مش مناسبة لده.

## تحديثات الأداء والسلوك في المكالمات الصوتية

### ١. تقليل الـ Latency
غير موديل Claude السريع (خطوة صح اتخذناها قبل كده)، فيه 3 حاجات تانية بتأثر على إحساس السرعة في المكالمة:

- **`startSpeakingPlan` / `stopSpeakingPlan`**: الإعداد الافتراضي عند Vapi بينتظر فترة أطول من اللازم قبل ما يعتبر إن الموظف خلص كلامه (ممكن توصل لثانية ونص تأخير حقيقي). ضبطناها في `call_tool.py` على قيم أقل (`waitSeconds: 0.4`) عشان الرد يحس إنه فوري.
- **`maxTokens: 200`** على الموديل - ردود قصيرة = وقت توليد أقل = إحساس أسرع، وده متسق أصلًا مع تعليمات "جمل قصيرة" في البرومبت.
- **`temperature: 0.2`** بدل الافتراضي - القيم المنخفضة بتساعد الـ caching عند المزود يشتغل، وده بيقلل زمن أول token.

النتيجة المتوقعة (حسب توثيق Vapi ومصادر خارجية راجعناها): تقليل ملموس في زمن الاستجابة، لكن الرقم بيختلف حسب الشبكة وموديل الصوت المستخدم - جرب وقيس بنفسك.

**خطوة تالية لو لسه مش سريع بما يكفي:** جرب موديل صوت (TTS) تاني غير `vapi/Elliot` الافتراضي - خيارات زي ElevenLabs Turbo أو Cartesia معروفة بسرعة أعلى، لكن محتاجة حساب/مفتاح API منفصل عندهم مش موجود في المشروع حاليًا.

### ٢. المكالمة مبتنهيش (كانت بتلف وتلخص في الآخر)
الحل مكوّن من جزئين لازم يشتغلوا مع بعض:
- **`endCallFunctionEnabled: true`** + **`endCallPhrases`**: بندي الـ assistant قدرة حقيقية إنه يقفل المكالمة (function call فعلي)، مش بس تعليمة نصية في البرومبت.
- **قسم "إنهاء المكالمة" في الـ system prompt**: بيحدد بالظبط إمتى المكالمة "خلصت" (تأكيد، رفض، طلب تأجيل، أو أي إشارة إنهاء)، وبيمنع صراحة إن الـ assistant يلخص أو يكرر الطلب في الآخر - أي توثيق مطلوب بيتستخرج من الـ transcript نفسه بعدين، مش لازم يتقال بصوت.

### ٣. الـ System Prompt بقى شامل أكتر
مبني على task dict عام (title/announcement/request/deadline) صالح لأي نوع مهمة HR، مش مقصور على "طلب تقرير". بيغطي: الأسلوب (جمل قصيرة، عدم التكرار)، التعامل مع الأسئلة عبر الـ Knowledge Base، وقاعدة إنهاء واضحة.

## الشات المتواصل (تبويب Chat لا ينسى السياق)

قبل كده كل أمر في تبويب Chat كان بيتعامل معاه بشكل منفصل تمامًا. دلوقتي فيه `CHAT_HISTORY` بيحتفظ بكل المحادثة (بما فيها الـ tool calls الداخلية)، فتقدر تقول "كلم فريق المبيعات" وبعدين "وكمان اعمل نفس الحاجة للتسويق" وهيفهم السياق. زرار **"New conversation"** فوق شمال تبويب Chat بيبدأ من الصفر لما تيجي تشتغل على موضوع مختلف تمامًا (مهم تستخدمه، لأن تاريخ طويل قوي بيكلف توكنز أكتر من غير فايدة حقيقية).

## شاشة Monitoring بقت حقيقية

قبل كده الشاشة كانت مبنية حوالين تاسك واحدة ثابتة بس. دلوقتي فيها قسم **"Recent Campaigns"** فوق بيلخص **كل** حملة اتنفذت (سواء من التاسك الثابتة أو من أي أمر Chat)، بعدد الإيميلات والمكالمات وآخر نشاط لكل واحدة. وجدول الـ Audit Log بقى فيه عمود **"Call Outcome"** بيوضح إزاي كل مكالمة خلصت بالظبط (طبيعي، محدش رد، الخط اتقطع، مشكلة تقنية...) بدل ما تعرف بس إن المكالمة "خلصت".

## متابعة التنفيذ والرد الذكي على الموظفين (أحدث إضافة)

بعد ما التاسك تتنفذ (إيميل أو مكالمة)، النظام بيتابع الردود عبر فحص صندوق الوارد (يدويًا أو بالجدولة التلقائية). لكل رد فعلي من موظف:

1. **Claude بيصنّف الرد**: تسليم فعلي / سؤال / طلب تأجيل / حاجة تانية غير متوقعة
2. **لو سؤال روتيني** وإجابته موجودة في تفاصيل التاسك أو في **Knowledge Base** (سياسات الشركة، قابلة للتعديل من تبويب Settings) → **الـ Agent بيرد بنفسه فورًا** كإيميل، ويسجل ده في الـ audit log
3. **لو أي حاجة تانية** (طلب تأجيل، استثناء، سؤال معقد، أو حاجة مش متوقعة) → بتتصعّد لقسم **"⚠ Needs Your Reply"** في تبويب Monitor، وHR Manager بيكتب رده مرة واحدة، والنظام بيبعته كإيميل فعلي للموظف

القاعدة الحاسمة اللي البرومبت بيتبعها: **الشك = تصعيد**. الـ Agent ماينفذش سياسة مش مذكورة صراحة في الـ Knowledge Base، ولا يوافق على استثناءات من نفسه.

المكالمات الصوتية كمان بتستخدم نفس الـ Knowledge Base - لو الموظف سأل سؤال روتيني **أثناء المكالمة نفسها**، الـ AI (Claude عبر Vapi) يقدر يرد لايف من غير ما يستنى إيميل.

### تجربة السيناريو
1. من تبويب Monitor، دوس **"Check Submissions"** (أو فعّل الجدولة التلقائية)
2. في وضع `MOCK_INBOX=true`، هتلاقي سلوك متنوع تلقائيًا: Sara بعتت (✅)، أحمد سأل سؤال روتيني (بيترد عليه تلقائيًا)، John طلب تأجيل (بيتصعّد لقسم "Needs Your Reply")
3. جرب تكتب رد في قسم "Needs Your Reply" وابعته - هتلاقيه اتسجل في Audit Log كـ `manager_replied`

## حدود مهمة في نسخة الديمو دي (لازم تعرفها قبل العرض)

- **مفيش حالة محادثة مستمرة** — لو Claude سأل سؤال توضيحي، لازم تكتب أمر جديد كامل (مش رد على نفس الجملة). ده تبسيط مقصود للديمو، مش قيد تقني دائم.
- **الموافقة على مستوى الخطة كلها، مش كل رسالة لوحدها** — في تبويب Chat، لما توافق على "Approve & Execute"، الإيميلات بتتصاغ وتتبعت **لكل المستلمين دفعة واحدة** من غير مراجعة كل واحدة لوحدها (بعكس تبويب Monitor اللي فيه مراجعة فردية). ده مقبول لأن الموافقة الأساسية (مين، وبأنهي محتوى) حصلت قبل كده على مستوى الخطة — لكن لو حاسس إنه محتاج مراجعة أدق قبل العرض على الإدارة، قولي نضيف خطوة "راجع كل مسودة" بين الموافقة والإرسال الفعلي.
- **CSV مش قاعدة بيانات حقيقية** — تعديلات Settings بتتكتب مباشرة في `employees.csv`، فمفيش تزامن آمن لو أكتر من شخص بيعدّل في نفس اللحظة.
- **الردود بترسل كإيميل جديد بعنوان "Re: ..."، مش threading حقيقي** (مفيش `In-Reply-To` headers) — كافي للديمو، لكن مش هيظهر كـ "reply" مربوط في كل عملاء البريد.
- **رسائل حالة النظام** (زي "تم الرد تلقائيًا") مكتوبة عربي ثابت بغض النظر عن لغة الواجهة المختارة، بعكس محتوى الإيميلات نفسها اللي بتتبع لغة الموظف بشكل صحيح.

## الأوامر المفتوحة (تبويب Chat) — الإضافة الرئيسية

اكتب أو قول أمر بلغة طبيعية، زي:
- "Email the Sales team asking for this week's numbers by Thursday"
- "اتصل بأحمد وسارة وذكرهم بموعد التقييم الأسبوع الجاي"

### إزاي بيشتغل تقنيًا
1. الأمر بيروح لـ `orchestrator.py` — بيستخدم Claude مع **tool use حقيقي**: أول تول `list_employees` (يجيب دليل الموظفين كامل بما فيه القسم)، وتاني تول `propose_plan` (خطة نهائية: القناة، المستلمين، المحتوى بالعربي والإنجليزي)
2. لو الطلب غامض (قسم مش موجود، تفاصيل ناقصة)، Claude بيرجع **سؤال توضيحي** بدل ما يخمّن ويستهدف حد غلط
3. الخطة بتتعرض في bubble للمراجعة — القناة، أسماء المستلمين (مش إيميلاتهم بس)، المحتوى، وسبب اختيار المستلمين دول
4. **لسه نفس مبدأ HITL**: لا حاجة بتتنفذ غير بعد ما تدوس "Approve & Execute"

### المايك (Voice Input) — طريقتين تختار بينهم من الواجهة

عندك dropdown في تبويب Chat اسمه **"STT engine"** فيه خيارين:

1. **Browser (Google)** — بيستخدم Web Speech API المدمجة في المتصفح. أسرع وأبسط، لكن بيحتاج المتصفح يقدر يوصل فعليًا لسيرفرات جوجل (لو عندك VPN أو فايروول بيمنعها، هيفشل بخطأ `no-speech` أو `network` من غير سبب واضح).
2. **Server (OpenAI)** — بيسجل الصوت (`MediaRecorder`) ويرفعه لسيرفرنا احنا، اللي بدوره بيكلم OpenAI Whisper. أبطأ شوية (فيه رفع فعلي)، لكن **مش محتاج وصول لجوجل خالص** — الحل الأضمن لو الشبكة عندك بتعمل مشاكل مع خدمات جوجل.

كل خطوة (طلب صلاحية، بدء التسجيل، سماع كلام، أي خطأ) بتظهر في **سطر debug تحت خانة الكتابة** — مفيد جدًا للتشخيص من غير ما تفتح Developer Tools.

فيه كمان dropdown تاني لاختيار لهجة العربي (`ar-EG`, `ar-SA`, `ar` عام) — لأن التعرف على العامية المصرية تحديدًا أضعف من الفصحى في محرك جوجل، فممكن تجرب أكتر من خيار تشوف أيهم أدق.

⚠️ **قيد مهم على الطريقة الأولى (Browser):** متاحة بس في Chrome / Chrome Android / Edge — مش شغالة في Firefox أو Safari. الطريقة التانية (Server) شغالة في أي متصفح حديث لأنها معتمدة على `MediaRecorder` بس (مدعوم بشكل أوسع بكتير).

جرب الطريقة التانية من غير حساب OpenAI: `MOCK_TRANSCRIBE=true` في `.env`.

## شاشة Settings — إدارة دليل الموظفين

بدل تعديل `employees.csv` يدويًا، من الواجهة تقدر: تضيف موظف جديد، تعدّل بياناته (بما فيها القسم — مهم عشان الأوامر المفتوحة تقدر تفهم "فريق كذا")، أو تمسحه. كل تعديل بيتكتب مباشرة في `employees.csv` نفسه.

## سيناريو الديمو القديم: طلب تقرير + متابعة تلقائية (Follow-up)

النسخة الأصلية (تاسك ثابتة: طلب تقرير مارس) لسه موجودة بالكامل في تبويب **Monitor** — مفيش حاجة اتشالت، بس بقت جنب القدرة الجديدة مش بديل عنها.

ده السيناريو الجاهز حاليًا في `task_definition.py`: النظام بيتصل بمجموعة موظفين يطلب منهم يبعتوا تقرير مارس بالإيميل، وبعدين بيتابع مين بعت ومين لسه لحد الديدلاين.

### إزاي يشتغل
1. **"اتصل بالكل (طلب أولي)"** — بيعمل مكالمة تفاعلية لكل موظف (عبر Vapi + Claude) تشرحله المطلوب والديدلاين، وتقوله يحط كلمة معينة في عنوان الإيميل (زي "تقرير مارس") عشان يتصنف صح
2. **"تحقق من الإيميلات"** — بيدور في صندوق الوارد (عبر IMAP) على إيميل من كل موظف فيه الكلمة دي في العنوان. لو لقاه، الموظف يبقى "بعت التقرير ✓"
3. لو الموظف لسه ملبعتش، بيظهرله زرار **"اعمل مكالمة متابعة"** — مكالمة بنبرة مختلفة شوية (بتذكّره إنها المرة التانية) وبتوضح لو الديدلاين قرّبت أو فاتت

### إعدادات الحملة
كل التفاصيل في `task_definition.py`:
```python
TASK = {
    "subject_keyword": "تقرير مارس",       # الكلمة اللي بندور عليها في عنوان الإيميل
    "check_since_date": "2026-08-25",       # ندور بس على إيميلات بعد التاريخ ده
    "deadline_iso": "2026-09-02T23:59:59",  # الديدلاين الفعلي (لحساب overdue)
    ...
}
```

### تجربة من غير حساب Gmail حقيقي (Mock Inbox)
حط `MOCK_INBOX=true` في `.env` — هيرجعلك نتايج وهمية (موظف واحد بس هيظهر إنه بعت، الباقي لسه) عشان تشوف شكل الواجهة كاملة.

⚠️ **ملاحظة مهمة:** فحص صندوق الوارد بيستخدم IMAP على نفس حساب Gmail بتاع الـ SMTP — لازم يكون الـ App Password شغال، وده معناه إن كل الردود بتوصل لصندوق وارد واحد مشترك (`hr-reports@...`)، مش لصندوق كل HR شخصيًا. في نسخة الإنتاج الحقيقية، ده أول حاجة هتتحول لصندوق مخصص أو نظام تذاكر حقيقي.

### الجدولة التلقائية
تقدر تخلي فحص "هل بعتوا التقرير" يتم لوحده بشكل دوري، بدل ما تضغط "تحقق من الإيميلات" يدويًا كل مرة. من الواجهة، فيه شريط "فحص تلقائي دوري":
- حدد المدة بالدقايق (مثلاً كل 60 دقيقة)
- اضغط **"تفعيل"** — من دلوقتي، السيرفر هيعمل الفحص لوحده كل المدة دي، وهيحدّث حالة كل موظف تلقائيًا
- تقدر تغيّر المدة أو توقف الجدولة في أي وقت من نفس المكان

⚠️ **ملاحظة:** الجدولة دي شغالة في الذاكرة بس (زي المسودات بالظبط) — لو عملت restart للسيرفر، هتحتاج تفعّلها تاني. وهي مبنية بـ `APScheduler` (background thread داخل نفس الـ process)، يعني مناسبة تمامًا للتست والديمو، لكن مش الحل الأنسب لبيئة إنتاج فيها أكتر من instance من السيرفر شغالة في نفس الوقت (هيبقى محتاج جدولة مركزية زي Celery Beat أو cron خارجي).

## المكالمات الصوتية التفاعلية (جديد)

الميزة دي بتستخدم **Vapi.ai** — بيدير الـ speech-to-text وtext-to-speech وturn-taking، وإحنا بس بنحدد الـ system prompt (اللي بيتصاغ من نفس تفاصيل التاسك) ونختار Claude كـ LLM بتاع المحادثة.

### إعداد Vapi (مرة واحدة بس)
1. سجل في [vapi.ai](https://vapi.ai)
2. من Dashboard → **Phone Numbers** → اشتري رقم أو استورد رقم Twilio عندك
3. من **API Keys** خد الـ private key وحطه في `.env`:
```
VAPI_API_KEY=...
VAPI_PHONE_NUMBER_ID=...
```
4. أضف رقم تليفون كل موظف في `employees.csv` (عمود `phone`، بصيغة دولية زي `+201xxxxxxxxx`)

### تجربة من غير حساب Vapi (Mock Mode)
زي `MOCK_CLAUDE`، فيه `MOCK_CALLS=true` في `.env` — بيخليك تشوف الواجهة والـ flow كامل من غير ما يتصل فعليًا بحد.

### إزاي تشتغل
من الواجهة، كل موظف عنده زرار **"اتصل بالموظف"** منفصل تمامًا عن زرار الإيميل — تقدر تختار تبعتله إيميل، تكلمه، أو الاتنين. المكالمة بتاخد وقت (مش فورية زي الإيميل)، فبعد ما تبدأها هتلاقي حالتها "المكالمة شغالة الآن"، وتقدر تضغط **"تحديث حالة المكالمة"** عشان تشوف لما تخلص ويظهرلك الـ transcript كامل تحت.

⚠️ **مهم:** المكالمات بتتحاسب بالدقيقة على Vapi (تقريبًا $0.05/دقيقة + تكلفة الموديل والصوت). ابدأ باختبار على رقمك الشخصي قبل أي موظف حقيقي.

## طريقتين للتشغيل: CLI أو واجهة ويب

### الطريقة 1: من الـ Terminal (`main.py`) — الأبسط
انتقل لقسم "التشغيل" تحت.

### الطريقة 2: واجهة ويب (`app.py`) — لمراجعة كل موظف بصريًا واعتماد كل واحد لوحده
```bash
uvicorn app:app --reload
```
افتح `http://127.0.0.1:8000` في المتصفح. هتلاقي:
- زرار "ولّد كل المسودات" — بيستدعي Claude لكل موظف ويعرض المسودة
- زرار "اعتمد وابعت" **لكل موظف على حدة** — مفيش "ابعت للكل" بضغطة واحدة، عمدًا، عشان تراجع كل رسالة
- جدول Audit Log بيتحدث لحظيًا تحت

⚠️ ملاحظة: حالة المسودات (draft) بتتخزن في الذاكرة بس (مش DB) — لو عملت restart للسيرفر، هتحتاج تولّد المسودات تاني. ده مقبول للتست، لكن في الإنتاج ده أول حاجة تتحول لجدول DB حقيقي.

## التشغيل

**1. جرّب أول حاجة بدون إرسال فعلي (dry-run — الافتراضي):**
```bash
python main.py
```
ده هيطبعلك مسودة كل إيميل (الموضوع + المحتوى) من غير ما يبعت فعليًا، ويسجلها في audit log بحالة `dry_run_only`.

**2. راجع المسودات كويس**، وعدّل `task_definition.py` لو عايز تغيّر التفاصيل.

**3. لما تبقى مطمن، ابعت فعليًا:**
```bash
python main.py --send
```
⚠️ ده هيبعت إيميلات حقيقية على الـ emails اللي في `employees.csv` — استبدلهم بإيميلات تجربة بتاعتك الأول قبل أي حاجة رسمية.

## مراجعة السجلات (Audit Log)

كل عملية (نجحت أو فشلت) بتتسجل في `audit_log.sqlite3`. تقدر تفتحه بأي أداة SQLite:
```bash
sqlite3 audit_log.sqlite3 "SELECT timestamp, employee_name, status FROM audit_log;"
```

## ده مقابل إيه من المعمارية الكاملة؟

الملف ده بيغطي جزء من الـ Orchestrator + Email Tool + Audit Log بس، من الوثيقة الأصلية.
**لسه ناقص عمدًا** (علشان ده MVP اختباري):
- **Guardrails / Risk Classification** — كل التاسكات هنا معاملة كـ "منخفضة الخطورة" تلقائيًا
- **Human-in-the-Loop Approval Queue** — الموافقة حاليًا هي إنك تشغّل `--send` بنفسك يدويًا بعد ما تشوف الـ dry-run
- **HRIS Integration** — البيانات هنا من CSV يدوي بدل نظام حقيقي
- **RBAC** — مفيش نظام صلاحيات، الكود بيفترض إن اللي بيشغّله هو HR Manager نفسه

الخطوة الجاية المنطقية: حوّل `--send` من فلاج CLI لـ approval queue حقيقي (endpoint أو جدول DB) قبل ما تضيف موظفين حقيقيين.
